Android 作为一个操作系统，有个核心特点是**生态开放**，可以自由地安装应用，Android 本身也有着较为丰富的系统机制

> 不过谷歌在近年来却逐步将这开放的生态**拉向封闭**，对于大部分使用场景这的确会更加安全，但也无疑给玩机增加了不少难度

## 为何玩机

原生 Android 虽然系统机制丰富，但是在功能上也无疑是实实在在的毛坯房，很多常用的功能可能只在各家的客制化系统上才有

不过就算是用上了类原生或者客制化系统，用着有些不如意也是难免的，为了使用体验更好，自然就要折腾折腾自己的系统，也就是玩机了

## 如何玩机

每个人玩机的目的可能各不相同，但是需求大抵都是一致的，那就是缺什么补什么，或者不要什么就去掉什么

例如在 iOS 的灵动岛设计刚推出时，在 Android 上最先可用的不是哪一家的客制化系统，而是第三方应用

这些应用通过全局悬浮窗来实现灵动岛功能，不需要嵌入到系统或者有系统权限，只需要通过系统提供的 API 就能够实现完整功能，只需要授予系统允许范围内的权限就能运行

或者如果想去掉一些广告，则可以用跳广告应用通过无障碍权限来模拟点击开屏广告上的 `✕`，省掉了手点这个步骤

也可以用本地代理应用通过 VPN 服务来屏蔽部分已知的广告域名，使应用无法加载广告资源，且无需修改系统的 `/system/etc/hosts`

当需要让应用获得更加丰富的功能时，也可以通过免 root Xposed 框架加载模块来实现

像这样通过各种应用就能满足各种需求，就是得益于 Android 的**开放性**

其系统除了与硬件交互、与 Linux 内核交互等底层逻辑外，大部分功能都是通过这样的一个个应用实现的，例如同时用于控制状态栏、控制中心等关键界面显示的**系统界面**

但是提供各种功能的应用再多，也没办法完全覆盖到所有需求

例如要禁用用不到但持续运行的系统应用来节约运行内存占用，或者不需要系统应用提供的功能，这显然是普通应用所无能为力的事情

这时候只能再从其他地方上看，Android 在这方面有两个较为方便的渠道：**ADB** 与 **DeviceOwner**

<Accordions>
<Accordion title='ADB 与 DeviceOwner'>

**ADB** 全称 **Android 调试桥**，从名字上就能看出是用于调试的途径，它的权限普遍高于普通应用

> 不过由于 Android 的逐步封闭以及 ADB 本身就与常规应用的能力集合不同，ADB 在一些方面的权限是不如普通应用能够触及得高的

并且身为调试功能，肯定不是为常驻高权限而设计的，通常只能通过其他设备进行有线或无线连接来使用，也可通过支持的应用来实现无线本地连接，但重启后均需重新连接

---

**DeviceOwner** 则是主要面向于企业管理应用而提供的功能，通过其 API 来控制当前设备功能，与 ADB 目的不同但部分可触及权限相同

通常可通过开机注册或 ADB 来将一个应用设为设备所有者，不过在开机注册之后设置需要退出掉所有账号，较为麻烦，并且有些客制化系统甚至还会阉割掉这个功能

> 有些应用会将自己的账号系统接入到系统中，通常包括系统本身以及一些与金融相关的应用，设置设备所有者需要将它们全部退出

因为是将一个应用设置为了设备所有者，所以该应用会持续拥有权限，不过由于常用功能所需权限不如 ADB 覆盖广且设置流程复杂，DeviceOwner 不如 ADB 实用

</Accordion>
</Accordions>

有了 **ADB** 或 **DeviceOwner** 权限之后，就能很方便地禁用掉系统应用了

不过通常不必卸载它们，因为系统应用的安装包往往位于只读的系统分区内，卸载后只是从应用列表中移除，并不会释放掉其占用的存储空间

> 更因为存储分区与系统分区都是单独的分区，就算真的释放掉了系统分区内的空间，也无法增加实际可用的存储空间
>
> 不过系统应用在更新后（通过应用商店等渠道更新而非直接更新系统），会在存储空间内新增新的安装包，并且系统应用在运行时也会产生一些数据
>
> 这时候可以用卸载更新功能来卸载掉存储空间内的安装包，此时才会真的释放可用的存储空间
>
> 并且卸载更新本身不会将系统应用从应用列表中移除，只是将其恢复至初始状态，无需重新安装

从这里就可以看出如果想要更好地玩机，想要更彻底地去折腾，就需要越来越高的权限，越低的权限只会遇到越多问题

例如使用特定应用会被环境检测严格的应用所检测，使用无障碍服务、VPN 服务由于 Android 系统机制，也都可以被其他应用检测到，又或是使用免 root Xposed 框架导致的完整性检测或是性能问题等

为了更好地去使用，例如隐藏掉这些应用或是服务，或是用更高的权限直接运行程序来省掉与 Android 交互的过程，最终的权限就是 Linux 中最高的权限：**root**

<Accordions>
<Accordion title='root 权限'>

**root** 是 Linux 中权限最高的用户，其 **uid** 为 `0`，Linux 通常会通过身份组来限制用户的实际权限，root 则可以基本无视这些限制

> 一般而言只将 **uid 为 `0`** 的用户视为 root，**gid 为 `0`** 但 **uid 不为 `0`** 可以当作只是被授予了较高的权限，**并不等同于 root**

在实际 Android 环境中，一个 **root** 进程往往还会受到 **capability** 与 **SELinux** 的限制

所以一般 **capability 满权限** 和 **SELinux 宽容或绕过 SELinux** 的 root 进程才能是 **完整 root**，否则都应视为 **受限 root**

> 一般来说获得完整 root 权限主要有两种途径：
>
> 一种是内核层直接为进程赋予完整权限并切换为 root，再为其绕过 SELinux 或切换为宽容 SELinux 域
>
> 另一种是在系统启动的早期阶段修改 SELinux 规则来获取宽容 SELinux 域，并在后续以 root 启动进程时使用该 SELinux 域
>
> 两种方式都能获取完整权限的 root，对于用户层的实际使用来说并没有区别

在 Android 中有一些系统进程始终以 root 权限运行，但因其受两者的限制，就算通过系统漏洞控制了进程，也并不一定能够获得较高的权限

</Accordion>
<Accordion title='Android 中的 root 使用'>

在 Android 的系统启动过程中，实际上总是会以 root 身份运行，因为无论是挂载系统还是执行其他初始化操作，都需要较高的权限

所有的初始化操作基本上都是由 Linux 内核启动的第一个进程 **init** 来执行的，它**本身为 root** 并**具有完整 capability 权限**，能够不受限地完成初始化操作

并且在系统初始化的早期阶段还一直会是宽容 SELinux 的状态，直到完成了一些关键的初始化操作，才会加载 SELinux 规则，让后续在受限情况下继续执行

不过就算是 SELinux 受限，init 本身仍为 root 并具有完整 capability 权限，它在系统启动时也会继续拉起各种进程

部分进程会在启动时切换 SELinux 域，并在拉起后立即降权，转为其他用户且执行 capability 降权，使权限彻底受限

部分进程会始终以 root 身份运行，但因 SELinux 和 capability 而也会受限

不过一些关键的系统进程例如 **zygote**，它会始终以 root 身份运行并也**具有完整 capability 权限**，除 SELinux 外基本没有限制

它会拉起 **system_server** 和**所有系统应用、普通应用**，并在其拉起后再降权，可将其视为负责应用进程相关的 **init**

所以对于正常使用 Android 的大部分情况都不会接触到 root，但是实际上都会经由 root，只是能够直接接触到的都是从 root 降权而来的罢了

> 所以在 Android 上获取 root 也可视为<del>拿回本该属于我的一切</del>？

</Accordion>
</Accordions>

<Callout type='warn' title='权限深池'>

root 权限很多时候可能会被视为破坏系统或者偷窃数据的威胁，抛掉刻板印象，实际上本以为较低的权限也有可能会做到这些

- 如果给应用授予文件管理权限，那么它就可以读取到设备上大部分的用户文件，包括文档、图片、视频等
- 如果给应用授予无障碍与自启动权限，那么它就可以通过全屏覆盖等方式阻止操控设备，重启后仍然会继续锁机
- 在使用 **ADB** 或 **DeviceOwner** 时如果禁用了关键的系统应用，就会导致系统启动失败或者系统功能异常

所以问题的来源无非就是两个：**应用滥权** 和 **错误操作**

如果应用开发者铁了心地要违法犯罪，那么就算不给应用任何权限，也会尝试通过系统漏洞越权提权

如果自己什么都不会也要铁了心地折腾，那么任何一个行为都有导致系统崩溃的风险

也就是说问题在于**自己如何用**与**用的东西如何跑**，无论是常规权限、ADB 或 DeviceOwner 权限，以及 root 权限，使用不当都会造成严重后果

只不过 root 权限能造成的后果更加严重，但不代表其他权限能造成的后果就会轻微

在玩机时不具备相关的知识或者不对风险操作加以确认，就很可能深陷这泥潭

</Callout>

## 深入玩机

root 作为最高的权限，想要获取自然会比前面所说的低权限要更复杂些，常规的方法就是解锁 **BootLoader** 后往 `init_boot`/`boot` 注入 root 实现

> 不过由于 Linux 内核已经是千疮百孔，并且厂商漏洞与泄露文件也已是并不少见，在现代设备上获得 root 权限往往可以**非常规**

<Accordions>
<Accordion title='非常规设备'>

对于模拟器或者虚拟机等技术而言，如果要使用 root，则需要看对 Android 系统的实现程度

如果只是做到了模拟，仿照真实系统做出了大部分系统能力，那么往往只能获得假性 root，因为一切都是模拟出来的

但如果实现了 Android 的整体功能，通过转译或者运行 Linux 内核等方式运行起了整个系统，那么在这个系统内的 root 能力会更加完整，只不过通常也不会影响到实体机内

</Accordion>
<Accordion title='BootLoader'>

BootLoader 是设备的引导程序，常见的引导分区有 `uboot`、`abl`/`xbl`/`efisp`、`lk` 等，通常会因处理器不同而异，它对设备启动的重要性是毋庸置疑的

所以现代设备上均会默认给 BootLoader 上锁，使得无法通过 BootLoader 自由刷写分区，要解除 BootLoader 的这道锁就称为**解锁**

要解锁 BootLoader 需要先启用 **OEM 解锁**，不过部分系统可能会隐藏常规的打开入口，只能通过特殊方法启用，也有的则会完全禁用掉这一功能

在启用 OEM 解锁后才会被允许在 BootLoader 模式下执行解锁命令，但部分设备会阻止进入 BootLoader 模式，或是解锁时需要解锁码之类的额外要求等

所以在层层限制下很多设备是无法正常解锁 BootLoader 的，只能通过官方渠道申请解锁，部分厂商则会完全不提供公开的解锁渠道

并且在解锁 BootLoader 后，除了会清除所有使用数据外，部分设备还会造成硬件或软件层面的熔断，导致 **TEE** 之类的安全环境损坏，从而使部分依赖受信环境的应用无法使用或功能受限

不过基于一些 BootLoader 漏洞和系统漏洞，或是被泄露出来的引导文件等，可以实现绕过厂商解锁限制来解锁，或是在解锁后重刷引导分区实现伪回锁等

> 部分系统甚至会完全不校验系统分区，在解锁并刷机后重新回锁也能正常使用

一些漏洞可以让 SELinux 变成宽容状态，从而可以在不解锁的情况下使用临时 root，在重启后需要重新激活，会因只能在开机后激活而在部分能力上受限

</Accordion>
<Accordion title='root 注入'>

在现代设备的启动过程中，Linux 内核会拉起 ramdisk 内的 init，而 ramdisk 往往位于 `init_boot` 或 `boot` 分区内，所以大致会有两种注入方案

> 对于有 `init_boot` 分区的设备，ramdisk 就在其中，反之则会存在于 `boot` 分区内，不过 Linux 内核会始终位于 `boot` 分区内
>
> `vendor_boot` 或 `recovery` 内的 ramdisk 有时也可作为被注入 root 的分区，不过往往不如前面两个常用

对于直接修改内核的内核 root 实现，通常会直接静态修补 `boot` 分区内的 Linux 内核

对于基于 LKM 的内核 root 实现或者纯用户态 root 实现，通常会替换 ramdisk 内的 init，在执行必要操作后再执行原始 init

> 前者会直接加载其 `ko`，后者则是在系统启动过程中执行初始化操作，例如注入 SELinux 规则等

这些 root 注入方案的目的都是获得不受限的完整 root 权限，最终都是服务于用户空间内的

所以大部分情况下内核 root 实现与用户态 root 实现并无区别，只是在兼容性、稳定性以及维护成本或使用方式上有着不同

</Accordion>
</Accordions>

在获得 root 权限后，能干的自然会更多

例如前面所说的本地代理，可以转为通过 **bind mount** 或 **overlayfs** 无需修改系统分区地挂载 `/system/etc/hosts`，或是通过 TUN 用虚拟网卡来实现透明代理，无需再经过 Android 的 VPN 服务

> 诸如此类的事情还有很多，例如通过挂载来获得更多系统功能，用完整 Xposed 框架来更自由地加载模块，以及使用更多 Linux 的底层功能等

总的来讲可以让环境被隐藏，或是功能更底层，对整个系统的操控能力会大大增强

<Callout type='warn' title='权力的双刃剑'>
  能干的越多，能干出祸来的自然也更多，给应用授予
  root，以及运行脚本或是可执行文件，在不知用途不知逻辑的情况下，都有可能造成数据丢失或是系统损坏
</Callout>

## 为何 ShiroSU

**ShiroSU** 作为一个系列项目，以系列中的各个项目围绕着玩机而提供不同方面的独特体验，在用什么 root、如何用 root 等问题上都能给出较好的答案

> ShiroSU 的 root 主线持续围绕着 root 相关内容而开发，其他项目在不同领域上也有着不同的建树，可在[主页](/)中查看

当在选择 root 实现时，可将目光放在 **ShiroSU NT** 上，它作为纯用户态 root 实现它提供了更好的兼容性与更低的侵入性，能在支持的设备上基本都能提供较好的使用体验

当已有 root 时，也可将目光放在 **ShiroSU Compat** 上，它作为支持多种 root 实现的 root 管理器，在不同 root 实现间都能提供一致的使用体验

### [ShiroSU NT](/newtech)

ShiroSU NT 对于常规设备，采用替换 ramdisk init 的方式进行注入

它对系统的启动流程基本没有过多干预，只会在系统加载 SELinux 规则时一并注入它所需的规则，并在系统启动时一并启动后端服务

> 得益于 ShiroSU NT 的低侵入性实现，它在 SELinux 宽容的设备或是模拟器及虚拟机上也能够正常启动

在安装 ShiroSU NT 后，即可通过在线的网页管理器进行使用，无需实体管理器应用，只需要以浏览器作为媒介

> 后端服务会以设备序列号为默认密码，确保了在默认情况下的安全性，不过在开始使用后也应当及时更换为强密码
>
> 并且使用网页管理器管理本质上只是用静态网页连接设备后端，两者间的交互无其他中间参与，与其他 root 实现安装管理器应用类似

通过局域网或者 ADB 端口转发等方式，也可以在其他设备上管理 root，不仅仅局限于本机操作

> ShiroSU NT 的后端默认会监听局域网，如果在公共网络中使用设备，应当将后端配置改为仅监听本地
>
> 不过通过其他设备管理也仍然需要密码校验，但只在私人网络内进行局域网互联是确保设备安全的行为

ShiroSU NT 在低侵入性的基础上还做到了高隐蔽性，作为白名单类型的 root 实现，不会泄露任何自身的挂载

在纯用户态实现的情况下也能做到规避普通应用的 SELinux 探测等

> ShiroSU NT 自带的隐藏功能也可以为黑名单应用卸载挂载，并在其运行期间暂时关闭后端端口来避免端口扫描

并且 ShiroSU NT 的整体实现趋于插件化，让它并不一定需要作为一个完整 root 实现来运行，它可以作为润滑剂来增强 root 生态

> 并且作为纯用户态 root 实现，ShiroSU NT 并不与内核层逻辑冲突，在使用 ShiroSU NT 时同样也可以静态修改内核或是动态加载内核模块

#### AI 适配

ShiroSU NT 采用网页管理器作为管理媒介，网页本身就是有利于 AI Agent 通过工具转换或视觉查看的，再加上 MCP 工具之类的功能，能够很好地让 AI Agent 辅助使用

再加上后端本身通过 RESTful API 设计实现，可以很好地用于网络交互，使得无论是在前端交互还是后端交互上，ShiroSU NT 都有着优秀表现

<Callout type='warn' title='AI 风险'>
  AI Agent 应当仅用于辅助判断之类的简单操作，让 AI Agent 完全控制设备的风险不言而喻
</Callout>

### [ShiroSU Compat](/compat)

ShiroSU Compat 针对多种 root 实现的权能与模块管理进行了适配，使得在不同 root 实现间都能通过 ShiroSU Compat 一个管理器进行管理

它提供了包括权能与模块管理在内的 root 管理功能，以及更多基于 root 实现的增强功能，在 root 管理器的基础上有着更多独特体验

它在一些实现上有着与 ShiroSU NT 一致的标准，使得在其他 root 实现上也能体验到这些内容
